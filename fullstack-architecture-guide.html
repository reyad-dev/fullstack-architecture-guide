تعلم Full Stack بالعربية

دليل مجاني لكل مطوّر Front-end يريد تعلّم تطوير Full Stack: خطة من 24 أسبوعًا، ومقارنة بين معماريات البرمجيات، وحاسبة للحمل والتوسع، ومنهج لتنظيم المشاريع الكبيرة مع قوالب جاهزة للاستخدام.

ابدأ بالخطة التعليمية اختر معمارية لمشروعك

لمن هذا الدليل؟ لمن لديه أساس في HTML وCSS وJavaScript ويريد فهم الخادم وقواعد البيانات والأمان وتصميم الأنظمة. ابدأ بخطة التعلم، ثم قارن المعماريات حسب احتياجات مشروعك. الفكرة الحاكمة: ابنِ بسيطًا، نظّم بوضوح، وقِس قبل أن تتوسع.

لوحةA-01

قبل أن تبدأ

ثلاث حقائق تحدد طريقة استخدامك لبقية هذا الدليل.

خلفيتك ميزة لا عائق

أنت تعرف TypeScript والمكونات وتجربة المستخدم. الفجوة الحقيقية في أربعة أشياء فقط: البيانات، والأمان، والتشغيل، وتصميم الأنظمة. هذه الخطة تركّز عليها.

الذكاء الاصطناعي يضاعف ما عندك

يسرّع من يفهم، ويُغرق من لا يفهم في أخطاء لا يراها. القاعدة الثابتة: لا تدمج كوداً لا تستطيع شرحه سطراً سطراً.

البساطة تربح غالباً

معظم المشاريع لا تحتاج Microservices أبداً. ابدأ بمونوليث معياري منظّم، وافصل جزءاً فقط عندما يثبت القياس أنه عنق زجاجة.

لوحةA-02

الخطة التعليمية: 24 أسبوعاً

سبع مراحل متتالية، لكل مرحلة مشروع تسلّمه ومعيار واضح يخبرك أنك أتممتها. افتح أي مرحلة لترى تفاصيلها.

إيقاعك الأسبوعي المقترح

12–15ساعة أسبوعياً، موزعة على 5 أيام
45%بناء فعلي بيدك
30%دروس وتوثيق رسمي
25%قراءة كود الآخرين وكتابة ملاحظاتك

لوحةA-04

المعماريات بالتفصيل

نوعان مختلفان يخلط بينهما كثيرون: معمارية النظام (كيف يُنشر ويتوسع) وتنظيم الكود (كيف تُرتّب الملفات داخله).

أولاً: معماريات النظام

المونوليث الطبقي

Layered Monolith
نقطة البداية

تطبيق واحد، وقاعدة بيانات واحدة، ونشر واحد. الكود مقسّم إلى طبقات: واجهة ثم منطق ثم بيانات.

[ Browser ] ──► [ App: UI + API + Logic ] ──► [ PostgreSQL ]

نقاط القوة

  • أسرع طريق من الفكرة إلى الإنتاج
  • تصحيح الأخطاء سهل: كل شيء في مكان واحد
  • Transactions بسيطة في قاعدة بيانات واحدة
  • أقل تكلفة تشغيل ممكنة

نقاط الضعف

  • يتحول إلى "كرة طين" إذا لم تُرسم حدود داخلية
  • يتوسع ككتلة واحدة حتى لو جزء واحد هو الثقيل
  • الفرق الكبيرة تتصادم في النشر والملفات
متى تختاره
MVP، أدوات داخلية، مشروع فردي بنطاق واضح.
الأدوات
Next.js full stack، أو Laravel / Django / Rails.

المونوليث المعياري

Modular Monolith
توصيتي الافتراضية

نشر واحد، لكن الكود مقسّم إلى وحدات بحدود صارمة (المستخدمون، الفوترة، المشاريع). كل وحدة تملك بياناتها، ولا تتواصل مع غيرها إلا عبر واجهة عامة.

┌────────────── App (one deploy) ──────────────┐
│  users/    billing/    projects/    notify/  │
│  each module exposes only its index.ts       │
└──────────────────────┬───────────────────────┘
                       ▼
          PostgreSQL (one schema per module)

نقاط القوة

  • بساطة المونوليث مع تنظيم الخدمات المصغّرة
  • أي وحدة يمكن فصلها لاحقاً كخدمة مستقلة بأقل جهد
  • مثالي للعمل مع الذكاء الاصطناعي: السياق محصور في وحدة واحدة
  • يكبر مع الفريق حتى عشرات المطورين

نقاط الضعف

  • يحتاج انضباطاً لمنع الاستيراد عبر الحدود (يُفرض بأدوات lint)
  • ما زال نشراً واحداً: خطأ في وحدة قد يوقف الكل
  • تخطيط الحدود يتطلب تفكيراً مسبقاً
متى تختاره
SaaS، أنظمة الشركات، المتاجر، المنصات المتوسطة والكبيرة. Shopify من أشهر الأمثلة على هذا النمط بحجم ضخم.
الأدوات
Next.js أو NestJS، PostgreSQL، Turborepo، وeslint-plugin-boundaries لفرض الحدود.

Serverless والمنصات الجاهزة

Serverless / BaaS
للإطلاق السريع

لا تدير خوادم. دوال تعمل عند الطلب (Vercel، Cloudflare Workers، AWS Lambda) أو منصة جاهزة مثل Supabase وFirebase توفر قاعدة البيانات والمصادقة والتخزين.

[ Client ] ─► [ Edge / CDN ] ─► [ fn /api/orders ] ─┐
                               [ fn /api/users  ] ─┴─► [ Managed DB + Auth + Storage ]

نقاط القوة

  • إطلاق خلال أيام
  • لا صيانة خوادم ولا تحديثات نظام
  • تتوسع تلقائياً مع الذروات
  • شبه مجانية في البداية

نقاط الضعف

  • ارتباط بالمزود يصعّب الخروج لاحقاً
  • الفاتورة تقفز بسرعة مع النمو
  • بداية باردة وحدود زمن التنفيذ
  • ضعيفة مع المهام الطويلة والاتصالات المستمرة
  • أخطاء أمنية شائعة مثل ترك Row Level Security معطلاً
متى تختارها
MVP لاختبار فكرة، مشاريع جانبية، تطبيقات بحمل متقطع.
شرط مهم
اكتب منطقك في طبقة مستقلة عن المزود حتى تستطيع الانتقال إن احتجت.

الموقع الثابت أولاً

JAMstack / Static-first
للمحتوى

الصفحات تُبنى مسبقاً وتُوزّع عبر CDN، والأجزاء المتغيرة تأتي من API أو نظام إدارة محتوى منفصل.

build ─► static HTML ─► CDN ─► Browser ─(fetch)─► API / Headless CMS

نقاط القوة

  • أسرع أداء ممكن وSEO ممتاز
  • سطح هجوم صغير جداً
  • تكلفة استضافة شبه صفرية

نقاط الضعف

  • غير مناسب لبيانات مخصصة لكل مستخدم أو متغيرة كل ثانية
  • زمن البناء يطول مع آلاف الصفحات
متى تختاره
مواقع الشركات، المدونات، صفحات الهبوط، التوثيق، كتالوج منتجات.
الأدوات
Astro، أو Next.js بالتوليد الثابت، مع Headless CMS مثل Sanity أو Payload.

خلفية مخصصة لكل واجهة

BFF — Backend for Frontend
نمط مكمّل

طبقة خلفية رفيعة لكل نوع واجهة (ويب، جوال) تجمع البيانات من الخدمات وتشكّلها كما تحتاجها الواجهة تماماً.

[ Web ]    ─► [ Web BFF ]    ─┐
                              ├─► [ Services / DB ]
[ Mobile ] ─► [ Mobile BFF ] ─┘

نقاط القوة

  • طلبات أقل وأخف لتطبيق الجوال
  • المفاتيح والأسرار تبقى على الخادم
  • كل واجهة تتطور دون كسر الأخرى

نقاط الضعف

  • طبقة إضافية للصيانة والنشر
  • تكرار المنطق إن وُضعت قواعد العمل فيها خطأً
متى تختاره
عندما يكون لديك ويب وجوال على نفس البيانات. ملاحظة: Route Handlers في Next.js تعمل كـ BFF بشكل طبيعي.

المعمارية الموجهة بالأحداث

Event-Driven Architecture
متقدمة

مكوّن ينشر حدثاً مثل "تم إنشاء طلب"، ومكوّنات أخرى تستمع وتتصرف بشكل غير متزامن دون أن يعرف بعضها بعضاً.

[ Orders ] ── OrderPlaced ──► [ Broker ] ──► [ Email ]
                                        ├──► [ Inventory ]
                                        └──► [ Analytics ]

لوحةA-06

التوسع وعدد المستخدمين

كيف تحوّل "عدد المستخدمين" إلى أرقام هندسية، ومتى تنتقل من طابق إلى الذي يليه.

"عدد المستخدمين" وحده رقم مضلل. الخادم لا يشعر بالمستخدمين، بل بالطلبات في الثانية وبالاتصالات المتزامنة. التحويل التقريبي:

الطلبات في الثانية وقت الذروة ≈ (المستخدمون يومياً × الطلبات لكل مستخدم ÷ 86,400) × معامل الذروة (عادة 3 إلى 5).
مثال: 100 ألف مستخدم × 60 طلباً = 6 ملايين طلب يومياً ≈ 70 طلباً/ثانية في المتوسط، ونحو 280 في الذروة. هذا حمل يتعامل معه خادم أو خادمان مع كاش جيد.

احسب لمشروعك

متوسط الطلبات في الثانية—
الطلبات في الثانية وقت الذروة—
مستخدمون متزامنون في الذروة—

سلّم التوسع: سبعة طوابق

الطابقالمستخدمون يومياًماذا تضيفعلامة الانتقال للطابق التالي
0. خادم واحدحتى 1Kالتطبيق وقاعدة البيانات على VPS واحد، أو منصة جاهزة.تحتاج نسخاً احتياطية موثوقة، أو الموارد تتجاوز 70% في الذروة.
1. قاعدة بيانات مُدارة1K – 10Kفصل PostgreSQL إلى خدمة مُدارة بنسخ احتياطي يومي، وCDN للملفات.استعلامات متكررة بطيئة، أو صفحات تُحسب مراراً بنفس النتيجة.
2. كاش وفهارس10K – 100KRedis للكاش والجلسات، فهارس مدروسة، Connection Pooling، مراقبة أداء.خادم التطبيق وحده لا يكفي حتى بعد الكاش، أو تحتاج نشراً بلا توقف.
3. موزّع أحمال100K – 500Kعدة نسخ من التطبيق بلا حالة خلف Load Balancer، وجلسات في Redis.قاعدة البيانات أصبحت عنق الزجاجة في القراءة، أو مهام ثقيلة تبطئ الطلبات.
4. نسخ قراءة وطوابير500K – 2MRead Replicas، وطوابير وعمّال خلفيون للبريد والتقارير والمعالجة.وحدة واحدة تستهلك موارد مختلفة جذرياً عن البقية، أو فرق تتصادم في النشر.
5. خدمات مستقلة وأحداث2M – 10Mفصل الوحدات الأثقل كخدمات، ونقل التواصل إلى أحداث عبر وسيط رسائل.قاعدة الكتابة الواحدة لا تكفي، أو تحتاج زمن استجابة منخفضاً في عدة مناطق.
6. تقسيم البيانات ومناطق10M فأكثرSharding، ونشر في عدة مناطق جغرافية، وفريق منصة متخصص.—

القاعدة: لا تصعد طابقاً لأنك تتوقع النمو، بل لأن علامة الانتقال ظهرت في المراقبة. كل طابق إضافي يضاعف تكلفة التشغيل وتعقيد الأعطال.

لوحةA-08

منهج العمل على المشاريع الكبيرة

دورة من عشر خطوات تتكرر مع كل ميزة. كل خطوة تترك أثراً مكتوباً في المستودع، فلا يضيع قرار ولا سياق.

المبدأ الحاكم: المستودع هو المصدر الوحيد للحقيقة. أي شيء لم يُكتب فيه غير موجود، لا لك بعد شهر، ولا لزميلك، ولا لوكيل الذكاء الاصطناعي في الجلسة القادمة.

  1. حدد المشكلة قبل الحل

    من المستخدم، وما مشكلته، وكيف نقيس النجاح، وما هو خارج النطاق صراحةً.

    docs/PRD.md

  2. قرر المعمارية واكتب السبب

    كل قرار كبير يُسجّل مع بدائله وعواقبه. لا يتغير القرار إلا بسجل جديد يلغيه.

    docs/ARCHITECTURE.md
    docs/adr/

  3. صمّم البيانات أولاً

    الجداول والعلاقات والقيود قبل أي شاشة. البيانات هي أصعب ما يتغير لاحقاً.

    docs/DATABASE.md
    packages/db/schema

  4. اتفق على العقد

    شكل الطلبات والردود وأكواد الأخطاء قبل التنفيذ، فتعمل الواجهة والخادم بالتوازي.

    docs/API.md

  5. قسّم إلى مهام صغيرة

    مواصفة لكل ميزة، ومهام لا تتجاوز يوماً واحداً، وكل مهمة لها اختبار يثبت اكتمالها.

    docs/specs/
    docs/TASKS.md

  6. نفّذ في فرع قصير العمر

    فرع لكل مهمة يُدمج خلال يوم أو يومين. الفروع الطويلة هي مصدر التعارضات المؤلمة.

    feature/invoice-pdf

  7. دع الآلة تحرس الجودة

    فحوص تلقائية قبل كل commit، وCI يمنع الدمج إن فشل أي فحص. لا استثناءات.

    .husky/
    .github/workflows/ci.yml

  8. راجع قبل الدمج

    قالب PR يجبرك على الوصف وخطوات الاختبار. حتى لو كنت وحدك، راجع الـ diff كأنه كود شخص آخر.

    .github/pull_request_template.md

  9. انشر على مراحل

    staging أولاً ثم الإنتاج، والميزات الكبيرة خلف Feature Flag، وخطة تراجع جاهزة قبل النشر.

    docs/DEPLOYMENT.md

  10. وثّق وتعلّم

    سجل التغييرات، وتحديث حالة العمل، وتحويل كل خطأ متكرر إلى قاعدة مكتوبة لا تُكسر.

    CHANGELOG.md
    docs/PROGRESS.md
    CLAUDE.md

# CLAUDE.md

## Project
<Name>: <one sentence: what it does and for whom>.
Read docs/PRD.md and docs/ARCHITECTURE.md before any change that touches more than one module.

## Stack
Next.js (App Router), TypeScript strict, PostgreSQL + Drizzle, Zod, Better Auth,
Redis + BullMQ, Vitest, Playwright, pnpm + Turborepo.

## Commands
- pnpm dev            # start everything
- pnpm lint           # must pass
- pnpm typecheck      # must pass
- pnpm test           # must pass
- pnpm db:generate    # create a new migration from schema changes
- pnpm db:migrate     # apply migrations locally

## Architecture rules
- Modular monolith. Code lives in apps/web/src/modules/<module>/
- A module imports another module ONLY through its index.ts
- Business logic lives in *.service.ts, never in route handlers or React components
- Database access lives in *.repository.ts only
- Every external input is validated with Zod at the boundary
- Server-only secrets never reach client components

## Conventions
- Files: kebab-case. Components: PascalCase. DB tables: snake_case plural
- Errors: throw AppError(code, message); never send raw errors to the client
- Dates are stored in UTC and formatted only in the UI
- Full list: docs/CONVENTIONS.md. Domain terms: docs/GLOSSARY.md

## Workflow
1. Read the task spec in docs/specs/ and docs/PROGRESS.md
2. Propose a short plan. Wait for approval before writing code
3. Make the smallest change that completes one step
4. Run lint, typecheck and tests after each step
5. At the end of the session, update docs/PROGRESS.md

## Never
- Never edit an existing migration. Create a new one
- Never commit .env files or secrets
- Never disable lint rules, TS checks or tests to make something pass
- Never modify a test to make it pass without asking
- Never add a dependency without asking first
- Never touch files outside the task scope without saying so

لوحةA-10

القواعد الذهبية وقائمة ما قبل الإطلاق

قواعد لا تُكسر في أي مشروع، ثم قائمة فحص تمر عليها قبل أن يرى أي عميل منتجك.

الفرع الرئيسي محمي

لا push مباشر إلى main. كل تغيير يمر عبر PR ينجح في CI.

Migrations للأمام فقط

لا تعديل لـ Migration منشورة، ونسخة احتياطية قبل أي Migration في الإنتاج.

الأسرار خارج المستودع

.env.example فقط في Git، والقيم الحقيقية في إعدادات المنصة أو مدير أسرار.

staging تطابق الإنتاج

نفس الإصدارات والإعدادات، ببيانات وهمية. ما لم يُجرَّب هناك لا يصل للإنتاج.

المراقبة من اليوم الأول

تنبيهات أخطاء، وسجلات منظمة بمعرّف لكل طلب، حتى تتبع أي مشكلة من أولها لآخرها.

نسخة احتياطية تُجرَّب

نسخ يومي تلقائي، واستعادة تجريبية كل شهر. النسخة التي لم تُستعد قط لا يُعتمد عليها.

أنواع موحدة من الطرف للطرف

من مخطط قاعدة البيانات حتى الواجهة، دون any ودون @ts-ignore.

العمليات المالية لا تتكرر

كل دفعة أو Webhook يحمل مفتاح Idempotency، فيُنفَّذ مرة واحدة حتى لو وصل مرتين.

المكتبات مثبّتة ومراقبة

lockfile داخل المستودع، وأداة مثل Renovate أو Dependabot للتحديثات الأمنية.

الميزات الكبيرة خلف مفتاح

انشر الكود مطفأً عبر Feature Flag، ثم شغّله تدريجياً لفئة صغيرة أولاً.

نقطة رجوع قبل كل جلسة

commit نظيف قبل أن يبدأ الوكيل أي عمل. التراجع يجب أن يكلّف أمراً واحداً.

لا كود لا تفهمه

إن لم تستطع شرح سطر لزميل، فهو لا يدخل الفرع الرئيسي.

أسئلةFAQ

أسئلة شائعة عن تعلم Full Stack

إجابات مختصرة تساعدك على اختيار نقطة البداية.

ما معنى تطوير Full Stack؟

تطوير Full Stack يجمع بناء واجهة المستخدم مع تطوير الخادم والتعامل مع قواعد البيانات. يتعلّم المطوّر كيف تنتقل البيانات من النموذج في المتصفح إلى API، وكيف تُتحقق المدخلات والصلاحيات، ثم كيف تُحفظ البيانات وتُعرض للمستخدم.

كيف أبدأ تعلم Full Stack إذا كنت مطوّر واجهات؟

راجع TypeScript وHTTP وGit أولًا، ثم تعلّم بناء API وقواعد البيانات والمصادقة. خطة التعلم من 24 أسبوعًا تربط كل مرحلة بمشروع تطبيقي ومعيار لإتمامها، وتشمل الاختبارات والنشر والمراقبة.

كيف أختار معمارية مشروع الويب؟

قارن نوع المشروع وحجم الفريق ومتطلبات التشغيل قبل اختيار النمط. اقرأ شرح المعماريات وجدول المقارنة، ثم جرّب أداة اختيار المعمارية. التوصية نقطة بداية تعليمية تحتاج إلى مراجعة متطلبات مشروعك.

هل عدد المستخدمين يحدد احتياج المشروع إلى Microservices؟

عدد المستخدمين وحده لا يكفي. راقب الطلبات في الثانية والاستعلامات وأوقات الاستجابة، مع احتياجات الفريق للنشر المستقل. استخدم حاسبة الحمل وسلّم التوسع لفهم التقديرات، ثم تحقّق باختبارات الحمل قبل تغيير المعمارية.
